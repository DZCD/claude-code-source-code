SDK 的默认模型客户端使用 Anthropic Messages 格式，可以对接任何 Anthropic
兼容端点，但每个 provider 对思考相关参数的支持子集不同。本页记录的内容
以 provider 官方兼容性文档和真实请求验证为准。

## OpenAI Responses API

*需要 0.31.0 及以上版本。*

`createOpenAIResponsesClient()` 创建使用 OpenAI `POST /v1/responses` 协议的
`ModelClient`。通过 `modelClient` 注入；默认客户端仍使用 Anthropic Messages。
仅修改智能体的 `baseURL` 不会切换协议。

```ts
import { createBareAgent, createOpenAIResponsesClient } from "agent-lattice";

const agent = createBareAgent({
  model: process.env.OPENAI_MODEL ?? "gpt-4.1",
  modelClient: createOpenAIResponsesClient({
    apiKey: process.env.OPENAI_API_KEY,
  }),
});

const result = await agent.prompt("Say hello");
console.log(result.result);
```

`apiKey` 和自定义 `baseURL` 应传给 `createOpenAIResponsesClient()`，
而不是智能体。工厂默认读取 `OPENAI_API_KEY`，地址默认为
`https://api.openai.com/v1`。自定义基础地址必须提供 `/responses`；
仅支持 Chat Completions 的端点不能使用。可选的 `fetch` 用于覆盖 HTTP 传输。
请求使用官方 OpenAI 客户端，关闭自动重试；HTTP 和协议错误转为 SDK `APIError`。

适配器支持文本、URL/base64 图片、函数工具（含并行调用）、包含文本/图片的工具结果、
JSON 输出、流式输出、取消和请求超时。工具执行、`outputSchema` 校验和补交机制
仍由现有 SDK 循环驱动。函数工具显式设置 `strict: false`，保留现有 schema 中
可选字段的语义。查询选项 `outputFormat: "json"` 映射为
`text.format.type: "json_object"`；JSON schema 映射为 `json_schema`，
设置 `strict: true`，名称为 `agent_output`。请提供 OpenAI strict 模式支持的
schema；适配器不改写 schema。使用 JSON 模式时，提示词也需要满足模型的 JSON 要求。

### 推理与会话历史

*需要 0.31.0 及以上版本。*

工厂的 `reasoningEffort` 接受 `none`、`minimal`、`low`、`medium`、`high` 和
`xhigh`；省略时使用 provider 默认值，各模型支持范围不同。智能体/查询上的
`reasoningEffort: "low"` 或 `"high"` 覆盖工厂配置；SDK 的 `"max"` 映射为
OpenAI `"xhigh"`（DeepSeek 的例外见下文）。除自 0.32.0 起的官方 DeepSeek
端点外，`thinkingConfig` 的 `enabled` 和 `adaptive` 会报错，
因为 Anthropic 的思考预算在此没有对应参数。
除下文说明的官方 DeepSeek 端点外，
`thinkingConfig: { type: "disabled" }` 会省略已配置的推理力度，补交阶段也如此，
但保留工厂上显式设置的 `none`。省略力度不保证 provider 关闭默认推理。若模型支持显式关闭推理，请在工厂上设置
`reasoningEffort: "none"`。

每次请求携带会话历史，设置 `store: false` 和
`include: ["reasoning.encrypted_content"]`。推理输出以
`OpenAIReasoningBlock`（`{ type: "openai_reasoning", item }`）保留在消息
`content` 内；assistant 文本在 `TextBlock.phase` 中保留可选的 Responses
`phase`。历史存储必须完整保留这些内容字段，内置 JSONL 存储已经支持。
它们属于会话内容，不是响应元数据。恢复后请继续使用同一协议和兼容模型；
此适配器遇到 Anthropic thinking/document 内容块会报错。

### 事件、用量与边界

*需要 0.31.0 及以上版本。*

`stream_event.event` 原样携带 Responses 事件（例如
`response.output_text.delta`），不会转为 Anthropic `content_block_delta`。
可根据增量显示文本，以最终 `assistant` 事件获取完整消息。
流缺少终止响应时会报错。用量沿用 SDK 现有的互斥分类：`input_tokens` 不含缓存命中，
`cache_read_input_tokens` 单独报告缓存命中，`output_tokens` 包含推理输出。
响应 ID 和实际模型仍通过 assistant 消息及 `ContextTracer` 提供。

此适配器不暴露 OpenAI 托管工具、文档输入、`previous_response_id`、后台任务或
WebSocket 模式。工具执行和会话历史由 SDK 管理。适配器有本地 HTTP/SSE 契约测试；
真实 provider 测试通过 `OPENAI_API_KEY` 和 `OPENAI_MODEL` 按需启用。

### 识图与生图

*需要 0.31.0 及以上版本。*

| 能力 | 本 SDK 的 Responses 适配器 |
| --- | --- |
| URL/Base64 图片输入，以及函数工具返回的图片 | 模型支持视觉时可用 |
| 原生 `image_generation` 托管工具及 `image_generation_call` 输出 | 未暴露 |
| Document/PDF、音频或视频输入 | 此适配器不支持 |

OpenAI 可通过 Responses 托管工具或独立 Images API 生图，但本 SDK 适配器没有
暴露这些托管工具。应用需要生图时，可把 Images API 封装成普通 SDK `tool()`；
这部分集成由应用实现。参见 [OpenAI 生图说明](https://developers.openai.com/api/docs/guides/image-generation)。

### DeepSeek Responses API

*需要 0.31.1 及以上版本。*

在 Responses 客户端工厂上设置 `baseURL: "https://api.deepseek.com"`，
智能体上设置 `model: "deepseek-flash"`。这与 DeepSeek 的 `/anthropic`
端点使用不同协议。DeepSeek 在 `item.content` 中返回明文推理内容，适配器通过
`OpenAIReasoningBlock` 原样保存并回传，不要求加密推理内容。

DeepSeek 开启推理时，不接受指定某个函数的 `tool_choice`。
自 0.31.1 起，工厂基础地址的主机名精确为 `api.deepseek.com` 时，
`thinkingConfig: { type: "disabled" }` 会发送
`reasoning: { effort: "none" }`。SDK 缺少交付后的补交恢复先通过此映射关闭推理，
再强制调用 `submit_output`。其他端点保留原有行为。
自定义 DeepSeek 网关若需要强制补交，可在工厂上显式绑定
`reasoningEffort: "none"`。

*需要 0.32.0 及以上版本。*

官方 DeepSeek Responses 端点现在接受现有的
`thinkingConfig: { type: "enabled", budgetTokens }` 和 `{ type: "adaptive" }`，
与其 Anthropic 端点一样开启思考。查询级开关可覆盖工厂上的
`reasoningEffort: "none"`；智能体/查询上显式设置的力度优先于工厂力度。
DeepSeek 在两种协议下都忽略 `budgetTokens`，因此这只是开关，不是思考 token 上限。
智能体/查询上的 `reasoningEffort: "max"` 原样发送为 `max`；其他 Responses
端点保留原来的 `max` 到 `xhigh` 映射。

DeepSeek 不允许在接收一个未带思考内容的工具调用结果时开启思考。
两个内置客户端都会让这次工具结果续写保持关闭思考，包括强制补交后
`submitOutputEndTurn: false` 的总结；下一次用户输入再恢复正常的思考配置。
历史中保留真实推理内容，SDK 不伪造思考文本或签名。

*需要 0.32.2 及以上版本。*

工具调用回复里带有 thinking 块时，即使块内文本为空，也算思考轮次，续写保持开启思考。
DeepSeek 在思考模式下接受回传这个空块；保持开关不变也能让前缀缓存继续有效，
因为 DeepSeek 不在开启思考和关闭思考的请求之间共享缓存前缀。
没有 thinking 块的工具调用，续写仍关闭思考。0.32.2 之前，空块会让本轮剩余请求全部关闭思考。

两种协议由同一个 SDK 循环执行 `submit_output` 契约：

| 行为 | 验证范围 |
| --- | --- |
| 默认提交即结束；`submitOutputEndTurn: false` 记录提交后允许总结 | 两种协议、流式/非流式、思考开/关实测 |
| 后一次合法提交覆盖前一次；schema 校验失败返回工具反馈供模型修正 | 两种协议、流式/非流式实测 |
| `agentTool()` 使用子级已校验的 `structuredResult`，即使子级最后输出了自然语言总结 | 两种协议、流式/非流式实测 |
| 混合/重复提交批次不执行 handler；截断调用不执行；缺少交付最多补交一次 | 确定性的 HTTP/SSE 协议对照测试 |
| 思考增量拼接后与完整思考一致，并保留在追踪中；中断丢弃未完成思考 | 两种协议实测 |
| Base64/URL 图片、多图顺序、带图片的工具结果可用于 `submit_output` | 两种协议实测 |

事件外壳和工具生命周期一致，provider 载荷保留原生格式。
Anthropic 使用 `thinking` 内容块和思考增量；Responses 使用 `openai_reasoning`
内容项，以及承载 DeepSeek 明文思考的 `response.reasoning_text.delta`。
OpenAI 的加密推理只原样保留，不伪装成明文思考。
此 Responses 适配器仍不支持 document/PDF 输入，遇到时明确报错；
图片测试通过不代表所有模态都已支持。URL 图片由 provider 下载，远端下载失败仍作为
`APIError` 返回；宿主已经持有图片、且不希望请求受远端可用性影响时，可使用 Base64。

在 `packages/agent-sdk` 下设置下文的真实测试环境变量后，可重复运行：

```bash
bun test ./src/__tests__/deepseekProtocolParity.integration.test.ts
bun test ./src/__tests__/responsesAnthropicParity.test.ts
```

已于 2026-10-29 使用 `deepseek-flash` 对官方的两种协议端点实测。
按需启用真实测试时，设置 `OPENAI_BASE_URL=https://api.deepseek.com`、
`OPENAI_MODEL=deepseek-flash`，并将 DeepSeek 凭据放在 `OPENAI_API_KEY` 中。参见
[DeepSeek Responses 兼容性说明](https://api-docs.deepseek.com/guides/responses_api/)。

协议参考：[Responses 迁移](https://developers.openai.com/api/docs/guides/migrate-to-responses)、
[推理历史](https://developers.openai.com/api/docs/guides/reasoning)、
[函数调用](https://developers.openai.com/api/docs/guides/function-calling)。

## DeepSeek

端点：`https://api.deepseek.com/anthropic`。DeepSeek 官方发布了
[Anthropic API 兼容表](https://api-docs.deepseek.com/zh-cn/guides/anthropic_api)，
下表把 SDK 选项映射到该兼容表。

| SDK 选项 | 线上格式 | DeepSeek 行为 |
| --- | --- | --- |
| `thinkingConfig: { type: "disabled" }` | `thinking: { "type": "disabled" }` | 生效，响应中不再出现 thinking 块。 |
| `thinkingConfig: { type: "enabled", budgetTokens }` | `thinking: { "type": "enabled", "budget_tokens": N }` | 思考会开启，但 DeepSeek **忽略 `budget_tokens`**——实际思考量可能远超预算，不要用它控制延迟。 |
| `thinkingConfig: { type: "adaptive" }` | `thinking: { "type": "adaptive" }` | 不报错且模型照常思考；DeepSeek 没有文档化 `adaptive` 取值，视同 `enabled`，不做任何保证。 |
| `reasoningEffort` | 顶层 `reasoning_effort` | 不在 DeepSeek 兼容表内，不生效。`reasoning_effort` 是 Kimi 的约定，见下文。 |
| `outputFormat` | `output_config.format` | 被忽略。DeepSeek 对 `output_config` 只支持 `effort`，SDK 的结构化输出不适用。 |

DeepSeek 自己的思考力度旋钮是 `output_config.effort`，SDK 目前尚未暴露，
所以在 DeepSeek 上唯一可靠的思考控制就是 `thinkingConfig` 的开/关。

其他值得知道的 DeepSeek 差异：

- 使用 `deepseek-flash` 或 `deepseek-v4-pro`。文档列出的 Claude 名称别名
  按 DeepSeek 的映射处理，其他不支持的名称会被拒绝。
- 消息历史里的 `thinking` 内容块被接受，`redacted_thinking` 块不支持。
- `max_tokens`、`system`、`stream`、`temperature`、`top_p`、
  `stop_sequences` 和工具调用完全支持；`cache_control` 一律被忽略。

## 默认输出预算

*需要 0.29.0 及以上版本。*

`baseURL` 指向官方 `api.deepseek.com`，且未传 `maxTokens` 时，SDK 使用 **393216 tokens（384K）**，与 DeepSeek 官方[模型元数据](https://api-docs.deepseek.com/api/list-models/)及[接口说明](https://api-docs.deepseek.com/api/create-chat-completion/)标注的最大输出一致。其他端点保留原来的 16384-token 默认值；显式 `maxTokens` 始终优先。请显式设置 `baseURL`；SDK 不通过环境变量判断输出预算。

这是单次模型请求的输出上限，包含 thinking 输出，不代表每次必须生成这么多 token。供应商可以提前结束响应，实际用量和计费按真实生成量计算。应用需要限制输出或成本时仍可显式设置较小的值。独立的 `autoCompact.maxTokens` 摘要预算不变。


## Kimi

Kimi K3 经 Anthropic 兼容端点/网关使用时，约定正好相反：它接受 SDK 从
`reasoningEffort` 发出的顶层 `reasoning_effort` 参数（`"low"`、`"high"`、
`"max"`），而不接受 `thinkingConfig`。省略 `reasoningEffort` 时 SDK 不发送
该字段，应用 provider 默认值（Kimi K3 为 `"max"`）。

Kimi 开放平台的 `https://api.moonshot.cn/v1` 是 OpenAI Chat Completions
协议，不是 SDK 内置 Anthropic 客户端可用的 `baseURL`。

## Anthropic

`thinkingConfig` 面向 Anthropic 官方 API：`adaptive`、固定
`budgetTokens`（封顶 `maxTokens - 1`）、`disabled` 都序列化为 Anthropic
官方的 `thinking` 线上格式，`outputFormat` 映射为 `output_config.format`。
例外是 `reasoningEffort`——它发送的是 Kimi 的顶层 `reasoning_effort`
参数，不是 Anthropic 字段。
