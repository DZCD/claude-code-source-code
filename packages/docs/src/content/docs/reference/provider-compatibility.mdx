The SDK's default model client speaks the Anthropic Messages format and works
against any Anthropic-compatible endpoint, but each provider honors a different
subset of the thinking-related parameters. This page records what actually
works, verified against the provider's official compatibility documentation
and live requests.

## OpenAI Responses API

*Requires 0.31.0 or later.*

`createOpenAIResponsesClient()` creates a `ModelClient` for OpenAI's
`POST /v1/responses` protocol. Pass it as `modelClient`; the default client
still uses Anthropic Messages. Changing the agent's `baseURL` alone does not
switch protocols.

```ts
import { createBareAgent, createOpenAIResponsesClient } from "agent-lattice";

const agent = createBareAgent({
  model: process.env.OPENAI_MODEL ?? "gpt-4.1",
  modelClient: createOpenAIResponsesClient({
    apiKey: process.env.OPENAI_API_KEY,
  }),
});

const result = await agent.prompt("Say hello");
console.log(result.result);
```

Put `apiKey` and any custom `baseURL` on `createOpenAIResponsesClient()`,
not on the agent. The factory defaults to `OPENAI_API_KEY` and
`https://api.openai.com/v1`. A custom base URL must expose `/responses`;
Chat Completions-only endpoints do not work. `fetch` optionally overrides the
HTTP transport. Requests use the official OpenAI client with automatic retries
disabled; HTTP and protocol failures become SDK `APIError`s.

The adapter supports text, URL/base64 images, function tools (including parallel
calls), tool results containing text/images, JSON output, streaming, cancellation,
and request timeouts. Agent tools, `outputSchema` validation and submission recovery
continue to run in the existing SDK loop. Tools use `strict: false` to preserve
existing optional schema fields. For structured responses, query
`outputFormat: "json"` maps to `text.format.type: "json_object"`; a JSON schema
maps to `json_schema` with `strict: true` and name `agent_output`. Supply a schema
supported by OpenAI strict mode; the adapter does not rewrite it. Follow the
model's JSON prompting requirements when using JSON mode.

### Reasoning and conversation history

*Requires 0.31.0 or later.*

The factory's `reasoningEffort` accepts `none`, `minimal`, `low`, `medium`,
`high`, and `xhigh`; omit it to use the provider default. Model support varies.
Agent/query `reasoningEffort: "low"` or `"high"` overrides the factory setting;
the SDK's `"max"` maps to OpenAI `"xhigh"` (see the DeepSeek exception below).
Except on the official DeepSeek endpoint since 0.32.0, `thinkingConfig` with
`enabled` or `adaptive` is rejected: Anthropic thinking budgets have no equivalent here.
Except for the official DeepSeek endpoint described below,
`thinkingConfig: { type: "disabled" }` suppresses configured reasoning effort,
including during submission recovery, but preserves a factory setting of `none`.
Omitting effort does not guarantee that the provider disables its default reasoning.
To explicitly request no reasoning on a compatible model,
set `reasoningEffort: "none"` on the factory.

Every request sends the conversation with `store: false` and
`include: ["reasoning.encrypted_content"]`. Reasoning output is preserved as
`OpenAIReasoningBlock` (`{ type: "openai_reasoning", item }`) inside message
`content`. Assistant text preserves the optional Responses `phase` as
`TextBlock.phase`. History stores must round-trip these content fields; the
built-in JSONL store does so. They are conversation content, not response
metadata. Continue a restored conversation with the same protocol and a
compatible model; Anthropic thinking/document blocks are rejected by this adapter.

### Events, usage and limits

*Requires 0.31.0 or later.*

`stream_event.event` contains native Responses events such as
`response.output_text.delta`; it is not converted into Anthropic
`content_block_delta`. Render text from the delta and use the final `assistant`
event for the complete message. A stream without a terminal response fails.
Usage follows the SDK's existing mutually exclusive buckets: `input_tokens`
excludes cached tokens, `cache_read_input_tokens` reports them, and
`output_tokens` includes reasoning output. Response ID and actual model remain
available on the assistant message and through `ContextTracer`.

This adapter does not expose OpenAI-hosted tools, document input,
`previous_response_id`, background jobs, or WebSocket mode. The SDK owns tool
execution and conversation history. The adapter is covered by local HTTP/SSE
contract tests; live provider tests are opt-in using `OPENAI_API_KEY` and
`OPENAI_MODEL`.

### Image understanding and generation

*Requires 0.31.0 or later.*

| Capability | This SDK's Responses adapter |
| --- | --- |
| URL/base64 image input and images returned by function tools | Supported when the model supports vision |
| Native `image_generation` hosted tool and `image_generation_call` output | Not exposed |
| Document/PDF, audio, or video input | Not supported by this adapter |

OpenAI offers image generation through its Responses hosted tool and a separate
Images API. The SDK adapter does not expose those hosted tools. Applications
can wrap the Images API in an ordinary SDK `tool()` when needed; that remains
application-owned integration. See [OpenAI image generation](https://developers.openai.com/api/docs/guides/image-generation).

### DeepSeek Responses API

*Requires 0.31.1 or later.*

Use `baseURL: "https://api.deepseek.com"` on the Responses client factory
with `model: "deepseek-flash"` on the agent. This is a separate protocol from
DeepSeek's `/anthropic` endpoint. DeepSeek returns reasoning as plaintext
`item.content`, which the adapter preserves and replays inside
`OpenAIReasoningBlock`; it does not require encrypted reasoning content.

DeepSeek rejects a forced function `tool_choice` while thinking is enabled.
Since 0.31.1, `thinkingConfig: { type: "disabled" }` sends
`reasoning: { effort: "none" }` when the factory's base URL has the exact
`api.deepseek.com` hostname. The SDK's missing-submission recovery uses this
mapping before forcing `submit_output`. Other endpoints retain their existing
behavior. Custom DeepSeek gateways can explicitly bind
`reasoningEffort: "none"` on the factory when forced-tool recovery is needed.

*Requires 0.32.0 or later.*

On the official DeepSeek Responses endpoint, `thinkingConfig: { type: "enabled",
budgetTokens }` and `{ type: "adaptive" }` enable thinking just as on its
Anthropic endpoint. A query-level switch overrides a factory setting of
`reasoningEffort: "none"`; an explicit agent/query effort takes precedence over
the factory effort. DeepSeek ignores `budgetTokens` on both protocols, so this
is an on/off control, not a thinking-token limit. `reasoningEffort: "max"` on
the agent/query is forwarded as `max`; other Responses endpoints keep the
existing `max` to `xhigh` mapping.

DeepSeek cannot enable thinking while consuming the results of a tool call
that was generated without thinking. Both built-in clients therefore keep
thinking off for that tool-result continuation, including the closing summary
when `submitOutputEndTurn: false` follows forced recovery. The next user prompt
restores normal thinking selection. History retains the actual reasoning;
the SDK does not invent reasoning text or signatures.

*Requires 0.32.2 or later.*

A tool call returned with a thinking block counts as a thinking turn even when
the block's text is empty, so the continuation keeps thinking on. DeepSeek
accepts the empty block back in thinking mode, and keeping the switch unchanged
keeps its prefix cache valid: DeepSeek does not share cached prefixes between
thinking-on and thinking-off requests. A tool call with no thinking block still
continues with thinking off. Before 0.32.2, an empty block turned thinking off
for the rest of the turn.

The same SDK loop enforces `submit_output` on both protocols:

| Behavior | Coverage |
| --- | --- |
| Default submission ends the run; `submitOutputEndTurn: false` records it and allows a summary | Live on both protocols, streaming/non-streaming, thinking on/off |
| A later valid submission replaces the earlier one; schema failures return tool feedback for correction | Live on both protocols, streaming/non-streaming |
| `agentTool()` uses the child's validated `structuredResult`, including when the child closes with prose | Live on both protocols, streaming/non-streaming |
| Mixed/duplicate submission batches execute no handlers; truncated calls do not execute; missing submission gets at most one recovery request | Deterministic HTTP/SSE transport parity tests |
| Reasoning deltas equal the final reasoning and survive tracing; interruption discards unfinished reasoning | Live on both protocols |
| Base64/URL images, ordered multiple images, and image-bearing tool results can feed `submit_output` | Live on both protocols |

The event envelope and tool lifecycle match; provider payloads remain native.
Anthropic uses `thinking` blocks and thinking deltas. Responses uses
`openai_reasoning` items and `response.reasoning_text.delta` for DeepSeek's
plaintext reasoning. OpenAI encrypted reasoning is preserved opaquely, not
exposed as fabricated plaintext. Document/PDF input is still unsupported by
this Responses adapter and raises an explicit error; image tests do not imply
support for every modality. URL images are downloaded by the provider; a remote
download failure remains an `APIError`. Use base64 for images already held by
the host when remote availability must not affect the request.

## DeepSeek

Endpoint: `https://api.deepseek.com/anthropic`. DeepSeek publishes an
[Anthropic API compatibility table](https://api-docs.deepseek.com/zh-cn/guides/anthropic_api);
the rows below map SDK options onto it.

| SDK option | Wire format | DeepSeek behavior |
| --- | --- | --- |
| `thinkingConfig: { type: "disabled" }` | `thinking: { "type": "disabled" }` | Honored. Thinking blocks disappear from the response. |
| `thinkingConfig: { type: "enabled", budgetTokens }` | `thinking: { "type": "enabled", "budget_tokens": N }` | Thinking turns on, but DeepSeek **ignores `budget_tokens`** — the model may think far beyond the budget. Do not rely on it for latency control. |
| `thinkingConfig: { type: "adaptive" }` | `thinking: { "type": "adaptive" }` | Accepted without an error and the model still thinks; DeepSeek documents no `adaptive` value, so treat it as `enabled` with no guarantees. |
| `reasoningEffort` | top-level `reasoning_effort` | Not in DeepSeek's compatibility table; no effect. `reasoning_effort` is a Kimi convention — see below. |
| `outputFormat` | `output_config.format` | Ignored. DeepSeek supports only `effort` inside `output_config`, so SDK structured output does not apply. |

DeepSeek's own thinking-strength knob is `output_config.effort`. The SDK does
not expose it yet, so on DeepSeek the only reliable thinking control today is
the on/off switch via `thinkingConfig`.

Other DeepSeek specifics worth knowing:

- Use `deepseek-flash` or `deepseek-v4-pro`. Documented Claude-name aliases
  follow DeepSeek's mapping; other unsupported names are rejected.
- `thinking` content blocks in message history are accepted;
  `redacted_thinking` blocks are not.
- `max_tokens`, `system`, `stream`, `temperature`, `top_p`, `stop_sequences`,
  and tool use are fully supported. `cache_control` is ignored everywhere.

## Default output budget

*Requires 0.29.0 or later.*

When `baseURL` points to the official `api.deepseek.com` host and `maxTokens` is
omitted, the SDK uses **393216 tokens (384K)**, the maximum output advertised by
DeepSeek's [model metadata](https://api-docs.deepseek.com/api/list-models/) and
[API reference](https://api-docs.deepseek.com/api/create-chat-completion/).
Other endpoints keep the existing 16384-token default. An explicit `maxTokens`
always takes precedence. Set `baseURL` explicitly to use this provider default;
the SDK does not inspect environment variables to choose the output budget.

This is a maximum allowance per model request, including thinking output, not a
request to generate that many tokens. The provider can end the response sooner;
usage and billing depend on tokens actually generated. Smaller explicit limits
remain useful when an application deliberately limits output or cost. The
separate `autoCompact.maxTokens` summary budget is unchanged.


## Kimi

Kimi K3 through an Anthropic-compatible endpoint uses the inverse convention:
it accepts the top-level `reasoning_effort` parameter that the SDK sends from
`reasoningEffort` (`"low"`, `"high"`, `"max"`), and it does not accept
`thinkingConfig`. When `reasoningEffort` is omitted the SDK sends nothing, so
the provider default applies (`"max"` for Kimi K3).

The Kimi Open Platform endpoint at `https://api.moonshot.cn/v1` uses the OpenAI
Chat Completions protocol and is not a valid `baseURL` for the SDK's built-in
Anthropic client.

## Anthropic

`thinkingConfig` targets the Anthropic API first: `adaptive`, fixed
`budgetTokens` (capped at `maxTokens - 1`), and `disabled` all serialize to
the official Anthropic `thinking` wire format, and `outputFormat` maps to
`output_config.format`. `reasoningEffort` is the exception — it sends Kimi's
top-level `reasoning_effort` parameter, not an Anthropic field.
