# 技术文档风格（写作 + 评审）

适用对象：API/SDK 文档、MDX、中英双语文档。核心立场——**文档是给人扫读的，不是给自己欣赏的**。每句话、每个标题、每个列表标签都要经得起"3 秒扫过能不能 get 到信息"。

## 写作原则（每条配真实例子）

### 1. 扫读优先：第一个词必须承载信息
标题、列表项的**开头名词/标签**是眼睛最先落的地方，必须信息密集。删掉空修饰词（聚焦／简单／强大／灵活／一站式）。
- ❌ `聚焦执行子智能体：完成一个明确 artifact…`（"聚焦"零信息，扫读不知道是啥）
- ✅ `` `implement` 子智能体：真正动手写代码…``（具体角色，一眼懂）

### 2. 列表必须平行
同一列表里各项的**形式和粒度**要一致。别在同一组里混用代码角色词（`explore`/`plan`/`review`）和中文短语（`聚焦执行子智能体`）。
- ✅ `explore` / `plan` / `review` / `implement` ——节奏统一。

### 3. 先定义后使用；用链接，别留悬挂术语
读者没见过的术语/API/概念，要么用一句话内联定义，要么链接到定义处。最糟的情况：一个词的意思在**另一篇文档**里，而本篇既不解释也不链接。
- ❌ 表格里写"需要 team runtime"，但全篇没说 team runtime 是什么（而这篇恰恰讲"没有 runtime"的模式）。
- ✅ 表格后补一句注解："这里的 **team runtime** 指……见 [Mailbox Team](…)"。
- ❌ `` `agentTool()` 暴露给模型的是一套标准输入：``（跳过了"它是什么"）
- ✅ 先点破"`agentTool()` 把子智能体包装成一个普通工具（返回 `ToolDefinition`）"，再讲输入。

### 4. 概念精确：别把两个东西搅成一个
用词要精确对应概念，不能含糊带过架构区别。最常见的坑：**model ≠ agent**。
- ❌ "当 supervisor **模型** 用…然后 supervisor 继续 agent loop"（讲运行时行为，主语应是智能体）
- ✅ "当 supervisor **智能体** 用…"
- ⚠️ 但当你**确实**指 LLM 本身时要保留"模型"："对 supervisor **模型**来说，这工具和别的没区别"——这里就该用 model。

### 5. 中文要通顺：拒绝名词堆叠，加连接词
中文不能把几个名词硬拼当主语，要有动词/结构。
- ❌ `Supervisor（主智能体） 子智能体委派适合…`（名词沙拉 + 多余空格）
- ✅ `Supervisor（主智能体）委派子智能体，适合…`

### 6. 翻译要忠实：别丢点
zh↔en 互译时，源文里的每个从句都有分量，别整句漏掉。
- 英文 *"This pattern does not require a team mailbox."* → 中文一度丢了这句，而它正是后面"何时用 mailbox team"的铺垫 → 必须补回。

### 7. 语体一致：别在一篇里混口语和书面
全篇统一 register。
- ❌ "拿回来" / "怎么验证"（口语）
- ✅ "以 `tool_result` 形式取回" / "如何验证"（与全文统一）

### 8. 推荐默认路径，别只罗列选项
列完参数/选项后，**明确指出推荐做法**，不要让读者自己挑。
- ✅ "大多数情况下直接用默认即可"（而不是只说"你可以传 X 也可以不传"）。

### 9. 给出"省略时会怎样"
每个**可选**参数都要交代默认行为，否则读者不敢省略。
- ✅ "`workspace` 不传时，SDK 按 `name` 自动分配 `~/.agent/workspaces/<name>/`，首次运行自动创建。"

### 10. 行为类描述要落在源码上
写默认值/报错/模式行为时，**先查代码再下笔**，别凭印象猜。

### 11. 双语同步
每次内容改动，**zh 和 en 两份都改**，别让它们漂移。

### 12. 抽象短语立刻接地气：跟一个括号例子
凡是偏抽象/行话的名词短语，紧跟一个**具体例子**（括号里给一两个真实名字）。读者靠例子秒懂，靠定义要绕半天。
- ❌ "lead 在内部协调命名成员"（"命名成员"是啥？）
- ✅ "把任务分派给几个有名字的成员（例如 researcher、reviewer）"
- ❌ "callable wrapper"
- ✅ "可调用的 wrapper（调用它就等于和工程负责人对话）"

### 13. 给接口前先给流程；划清"你实现什么 / runtime 替你做"
让读者实现一个接口/API 时，**先把它的生命周期/流程亮出来**（最好一张迷你状态图或时序），并点明"这部分你写、那部分 runtime 替你驱动"，再给接口签名和骨架。别甩一坨方法+状态让读者自己反推怎么用。
- ❌ 直接给 `TeamMailbox` 的 5 个方法 + 6 个状态，不说是谁、何时调用。
- ✅ 先给流程图 `send()→pending --claimNext()--> processing --updateStatus()--> done|failed`，点明"状态流转由 runtime 驱动，你的 adapter 只负责存取"，再给骨架。

### 14. 翻译卫生：中文里别留英文残片；术语映射全篇统一
中文句子里别夹生英文词（有现成中文就用），同一个英文术语的译法**全篇统一**。
- ❌ "claim 消息" / "mailbox work" / "raw mailbox tools" / "accepted handoff"（夹生 + 与别处不一致）
- ✅ "领取消息"（与 `team_read` 的"领取"统一）/ "mailbox 任务" / "底层 mailbox 工具" / "已接收的 handoff"（与首段统一）

### 15. 标准化术语时，grep 全部文档改干净
统一一个术语的译法/措辞时，**grep 整个文档集**，每一处都改，别只改当前页（否则一处新词、别处旧词，更乱）。
- 统一"行动模式"→"调用模式"时，发现 `public-api.mdx` 也用了"行动模式"，一并改掉。

## Review 清单（逐句扫一遍）

评审一段文档时，按这个顺序自问：

1. **第一个词有信息量吗？** 有没有"聚焦/简单/强大"这类空词？
2. **列表平行吗？** 同组项的形式/粒度一致吗？
3. **有悬挂术语吗？** 每个术语读者都见过，或本篇定义了，或链接了？
4. **API/概念先定义后用了吗？** 是不是一上来就讲"它暴露什么输入"却没说"它是什么"？
5. **概念用准了吗？** model/agent、一次性/持久、runtime/mailbox 这类有没有混？
6. **中文通顺吗？** 有没有名词堆叠、缺连接词、多余空格？
7. **翻译漏点了吗？** 跟英文源比对，有没有整句意思丢失？
8. **语体一致吗？** 口语/书面有没有混用？
9. **给了推荐默认吗？** 还是只罗列选项？
10. **可选参数写了"省略时的行为"吗？**
11. **行为/默认值查过源码吗？**
12. **zh 和 en 都同步改了吗？**
13. **抽象短语接地气了吗？** 跟了具体例子吗？
14. **让读者实现的接口/API，先给流程了吗？** 划清了"你实现 / runtime 做"吗？
15. **中文里有夹生英文残片吗？** 同一术语译法全篇统一吗？
16. **统一术语时，grep 全部文档改干净了吗？**（不只当前页）

## 评审输出格式

发现问题时，按优先级分组、给具体改法，而不是泛泛而谈：
- **必改**（语法坏句、丢翻译点、悬挂术语、概念错误）——给出 old→new。
- **小修**（语体、空格、并列、平行）——给出 old→new。
- 最后问一句"要我把必改/全部应用吗"，等确认再改，**zh + en 一起改**。

## 操作要点（构建 / 集成）

文档站本身的构建配置也归这套风格管。几条踩过的坑：

- **加任何 Astro/Starlight 集成插件后，立刻 `bun run build` 验证**，别只看 peer 警告就以为能用——peer 警告常常就是真不兼容的信号。
- **Astro 7+ 不要用基于 remark/rehype 的 mermaid 集成**（`@pasqal-io/starlight-client-mermaid`、`astro-mermaid` 等）。Astro 7 把 markdown 处理器换成了 satteri，不再执行 `markdown.remarkPlugins`：这类插件要么标记了 ` ```mermaid ` 却不生效，要么自带的 `MarkdownContent.astro` 在 Astro 7 下编译失败。要图就先用 ASCII，或走**客户端 `mermaid.run()` 方案**（在 DOM 里后处理 `code.language-mermaid`，绕开 satteri）。
- **框架大版本升级后，老的 remark/rehype/MDX 类集成一律重新验证**——markdown 管线是破坏性改动的高发区，版本号"满足"不等于真能跑。
